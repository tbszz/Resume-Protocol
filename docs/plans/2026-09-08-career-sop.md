# 岗位与回答逻辑：dbs 概念拆解及知识库方案

## 拆解

“匹配”混合了检索相关、资格符合、用户愿意投递三个概念。标题关键词只能帮助检索，不能证明招聘门槛或候选人能力。需要通过检索→资格证据→偏好→行动建议逐层判断。

这是需要工程实现和评测的 Problem，不是加一句提示词就能回答的 Question。dbs 用于明确概念边界，不充当招聘专家或权威招聘数据来源。

## 当前落地

- knowledge/career-sop.md 为版本化决策规则，由服务端读取并注入每次主模型调用。
- careerPolicy.js 确认用户明示的地区与招聘类型，不从学校地址或旧助手答案推断。
- jobEligibility.js 拦截已识别的地区、招聘类型、毕业届别冲突；无法确定的情况保守待核实。
- careerAgent.js 阻止未检索却直接输出岗位名单，去除历史非结构化助手内容的事实作用。
- knowledgeBase.js 移除两段项目、六项技能和奖项的凑数门槛。
- careerPolicy.test.js 覆盖上述反例。完整 npm test 通过；真实模型在无搜索范围时先问地区和类型，没有编造岗位。

## 应建设的四类资料

1. SOP：触发条件、必要输入、判断步骤、不可做事项、输出结构、拒绝与追问分支、规则ID、版本。先使用可审查Markdown/JSON，不必先引入向量数据库。
2. 招聘事实：官方URL、完整JD原文、抓取时间、发布日期、截止/在招状态、硬条件原句。动态更新，与SOP隔离。现有GitHub摘要仍然只是线索，尚未建立覆盖国内招聘的完整实时JD库。
3. 脱敏案例：真实原句、目标JD、修订稿、修改理由、事实边界、人工评审结论。不能把历史模型输出或“成功简历”直接视为正例；不能复用他人经历。
4. 评测集：好/坏答案成对记录，预期排除项和追问项，事实引用准确率、硬条件误推荐率、建议可执行性。录用结果受多因素影响，不直接当模型正确性的唯一标签。

## 优先级和限制

先运行SOP与反例回归，再补官方JD覆盖和人工审校案例。案例数量增长后，再考虑按场景检索，不能让检索结果覆盖硬规则。当前未训练模型、未引入向量库，也未完成开放职位全量验证；自然语言资格抽取仍需扩大人工标注评测，不能承诺所有门槛都已识别。
